# msfs-ui, the menu mod (1.0)

The part of MSFS-UI that runs inside the MSFS 2024 main menu. It is one ES2017 module, `dist/main.js`, which MSFS-UI-GENERATOR embeds and copies into the Community package as `html_ui/msfs-ui/main.js`. The app also writes the user's settings next to it, as `html_ui/msfs-ui/config.js` (see [Contracts between the app and the mod](../docs/development.md#contracts-between-the-app-and-the-mod)).

Node is needed only to build the mod, never on the user's machine.

## Commands

Run them from `mod/`:

```powershell
npm install          # once: esbuild, TypeScript, Ajv, Node types (exact versions)
npm run build        # dist/main.js, after every check below (with an inline source map)
node build/build.ts --release   # the same without the source map: the module shipped in the app
npm test             # unit tests (node:test); needs a build first (src/generated/)
npm run check        # build, then tests
```

To try the mod in the sim, use the developer tool of the app:

```powershell
generator\MsfsUi.DevTool\bin\Debug\net10.0-windows\msfs-ui-dev.exe install [--settings file]
msfs-ui-dev reload                       # hot reload while the sim runs
msfs-ui-dev console "[msfs-ui]"          # the mod's log
msfs-ui-dev eval "window.__msfsUiRuntime.settings"
msfs-ui-dev check                        # compatibility, offline and live
```

`--settings` takes a file in the app's settings format:
- `{ "schemaVersion": 1, "features": { "<id>": { "enabled": …, "options": { … } } } }`;
- without it, `%LOCALAPPDATA%\MSFS-UI-GENERATOR\settings.json` is used if it exists, otherwise the defaults of `features.json`.

## Contracts with the app

| File | Content | Read by |
|---|---|---|
| `features.json` | Every feature: id, title, description, screen, `enabledByDefault`, typed options (`boolean`, or `number` with `min` / `max` / `step` / `unit`) and their defaults | The build (typed settings, consistency checks) and the app (Features page, settings validation) |
| `compat.json` | What the mod takes from the sim: readable exports, screens, the sim's components it creates (with the attributes, states, values and children it uses), anchors, data-model symbols, files, CSS variables, translation keys, live checks | The app's compatibility check |
| `schema/*.schema.json` | JSON schemas of both files | The build (Ajv) and editors (`$schema`) |
| `test/fixtures/config.*.js` | Settings modules generated by the app (`ConfigScript`) | `ModContractTests` (C#) writes and compares them; `config-contract.test.ts` reads them with the mod's code |

After a change of `features.json`:
1. Run `dotnet test generator/MsfsUi.slnx` with `MSFS_UI_UPDATE_FIXTURES=1` to rewrite the fixtures.
2. Run `npm run check` here.

The version in `package.json` and the `modVersion` of `features.json` must be equal.

## What the build checks

`build/build.ts` stops with exit code 1 on the first failing step:

1. `features.json` and `compat.json` match their schemas. The catalogue also passes the rules a schema cannot express: unique ids, `min ≤ max`, and defaults within range and on the step grid.
2. `src/generated/catalog.ts` is generated from `features.json`: the `Settings` type, `FEATURE_IDS` and the specs used to validate `config.js`. It is not committed.
3. Feature modules match the catalogue:
   - each feature has its module, `src/features/<id-in-kebab-case>.ts` or a folder of that name;
   - it reads every one of its options as `settings.<option>`;
   - it is registered in `src/features.ts`.

   The registry's type also refuses a missing or unknown feature id.
4. Everything the sources take from the sim is listed in `compat.json`:
   - screen and component GUIDs;
   - `name="…"` anchors, or children declared by a component;
   - `TT:` translation keys;
   - named imports of `/Global/…` modules;
   - `coui://html_UI/VFS/…` files;
   - the sim's CSS variables (`--color…`, `--fontSize…`, `--unscaledScreenHeight`, `--backgroundOpacity`).
5. No raw U+2028 / U+2029 in the sources: build them with `String.fromCharCode`.
6. `tsc` on the mod (`tsconfig.json`) and on the Node code (`tsconfig.node.json`, build and tests), both strict.
7. esbuild bundles `src/main.ts` into `dist/main.js`:
   - target ES2017, ASCII output, inline source map (none with `--release`);
   - the sim's `/Global/*` modules stay external, `.css` files are imported as text;
   - the module is then refused if it has an operator before `await` (`!await x`), which Coherent GT does not load.

## The sim's own components

What the mod shows is made of the sim's components wherever one exists, so that it looks and behaves exactly like the sim: markup, visual states (hover, selected, disabled), sounds and accessibility. `src/sim/components.ts` creates them; verified on sim 1.9.18 (`fs-base-ui` 0.1.10):

- `window.ResourcesManager.createElementFromGuid(guid, factory)` builds a component from its cooked template (`cookedcomps/{GUID}.html` and `.json`). `factory` only needs `createElementFromName(tag)`, which creates the bare `ui-resource-element`.
- Once `loadingList.whenAllLoaded` (and the manipulator's `refLoadingPromise`) resolve, `manipulator.activate()` is called, as the sim does for the components it creates on the fly. On dispose: `manipulator.deactivate()`, then removal.
- Exposed attributes (`Title`, `Text`, `Icon`, `Status`…) are set with `setExposedAttribute`; selection and disabling go through the component's traits: `traits.selectable.Set(true)` selects it, `traits.deactivable.Set(true)` disables it.
- A component whose template has no `selectable` trait (`TextTab`) gets one with `AttachTrait(element, 'selectable', trait)`, the trait being found by its `traitName` in `GuidToTrait`; it is detached with the component.
- Clicks reach the component as ordinary `click` events (its template sets `data-input-group`).
- The template positions the component in the sim's own layout: here it fills a host element that the feature's CSS sizes. A component made for larger sizes may need a layout rule on one of its children (the weather bar resizes `TileButton`'s `CornerWhite`, centres its `Content` and gives its `Background` the icon buttons' gradient; the favourites set `Marketplace_Tile_Horizontal`'s `Title` and `Creator` sizes; the presets dropdown moves its `Content` 12 units in and its `List`); such children are declared in `compat.json`.

Components used:
- `TileButton` (choice tiles; in compact hosts, `msfs-ui-compact-tile` in theme.css centres the title on one line and reduces the selection corner);
- `IconButton_Squared` (icons), `TextTab` (tabs), `TextButton_Small` (buttons; the gallery's Hidden and Favorites get the mod's icon before their `Text`, in the button's content row);
- `FreeFlight_IFR` (flight category, whose colours are the component's own exposed values);
- `ImageButton_Livery` (the large livery and the grid's small ones: `manipulator.setData(image, onClick)`; `Selected` outlines the shown one; its host is dimmed when unavailable);
- `Dropdown` (the Showcase panel's variants, as the gallery's sort), `IconButton_Squared` (the large livery's arrows: `Icons/General/ArrowFull.svg`, the left one turned by `--rotation: 180deg` on the component, disabled at the ends by the component's own state) and `TileButton_Watermark_Small` (the sim's Configure tile, see below);
- the mod's own icons (`core/icon-toggle.ts`, SVG in `currentColor`, not the sim's components: the owner's choice): a heart for the favourite liveries (empty; full for a favourite; white) and a slashed eye for the hidden aircraft; a click does not reach the tile under it;
- `Search_Input` (text fields, see below);
- `TileButton_Fleet` (gallery tiles: the mod writes AircraftImage and three lines of text, as the sim's `SetData` would: the name in AircraftName, the variant in Subtitle, the studio in Distance, which moves up to Subtitle when there is no variant. The tile's own `State_Distance` shows that third line, but its Disabled state hides it again for good, so the CSS shows it (`has-third-line`). Its template splits its height 1.4 (image) to 1.2 (text banner): the image area keeps that height (`--tile-image-h`) and the banner only takes its three lines. In Showcase the banner has four lines, 96 units (`BANNER_UNITS`): the model in AircraftName, the brand in Subtitle (in the name's bold style), the variant in Distance (empty when there is none), and the studio on the banner's lowest line, in the mod's own line in the sim's Distance style (`msfs-ui-gal__studio`, inside the tile's `Text`); each line is held at one height and a text too long has its font reduced to fit (`TextFitter`, `fitBanners`), the sizes reset when a slot of the pool leaves Showcase; the names come from `sim/aircraft-names.ts` (the display name alone on the model's line when the model or the brand is empty). The tile's own `tileClick` / `tileHover` events, which carry no data then, are stopped at its host, and the mod sends its own with the aircraft);
- `Marketplace_Tile_Horizontal` (the gallery's list rows and the Free Flight favourites: Image, Title, Creator; in the gallery on one line centred in the row, the name in the bold Title, "- studio - variant" in the light Creator; its rating, separator, price banner and own heart are hidden, the mod's icon (the eye of an aircraft, the heart of a livery) is in the row's top right corner; its `ImageBlock` takes the thumbnails' ratio, 720 × 344, since its own wider box with `object-fit: cover` cut a quarter of each thumbnail; its manipulator gets an owned `item`, which its hover handler reads. On Free Flight it keeps its own two lines: the name, then "variant · livery · tail number", the text stopping before the row's corner icon, the heart);
- `Dropdown` (the gallery's sort and the weather bar's added presets: `setData(items, current)` with `{ title, selectedCallback }` items, `setEmptyTitle`, `List_Size` = 33 units per item + 9: items of 30, 3 apart, 6 of padding above and below, in its `List` › `real-scroll`, a virtual list of the sim that recycles about 15 items whatever their number). Its template places the list 30 units under its top; the weather bar puts it right under the dropdown (`top: 100%`), the sim's own 6 units above the first item, and sizes it toward the map's buttons, over what is under it (`dropdownListToward`, `sim/dropdown-list.ts`, tested; the owner's choice, 2026-11-01): whole items only, as many as leave above the higher of the map buttons (`Worldmap_Filters` › `Buttons`) and the map's scale (`Worldmap_Filters` › `ScaleBlock`, under the list) the gap nearest the one between the map buttons and the `EFB` button (26 pixels at 1164 lines), never under 6 units; all the items, 6 units under the last, when they fit; a list that scrolls ends on its last whole item's bottom (n x 33 + 3 units and half a pixel), the next item 3 units under its edge. Measured at each 250 ms pass, `List_Size` written when it changes; without the map buttons, down to the panel's bottom; upwards to the column's top when fewer than 3 items fit. The list keeps its scroll position from one opening to the next (in the middle of an item after a change of resolution): the bar scrolls it on opening, by the items' spacing on the screen, and for a chosen preset past the top edge less the gap between items (`dropdownScrollPosition`, rounded to the pixel), so that the previous item is hidden and the chosen one shows whole at the top.

Lists that scroll use the sim's own scrolling element, `<real-scroll direction="y">` (created as in the sim's cards: `createRealScroll`, `sim/real-scroll.ts`): it scrolls on the wheel and draws the sim's scroll bar (`ui-scroll-bar`, disabled while the content fits). Children appended to it go into its content (`.scroll__content`, a plain block that the feature's CSS may turn into a flex container of wrapped rows, with room on the right for the bar; the gallery computes its columns on the content's `clientWidth`, which the bar already narrows); it is emptied child by child, never with `innerHTML`, which would remove its own structure. Its API: `currentScroll`, `maxScroll`, `scrollToPosition(px)`, `updateSizes()`, and a `ui-scroll` event on every move. The bar sits beside the content in `.scroll__bar-container`, 0 wide while the content fits and 10 pixels at 1440 lines once it scrolls (from the next frame).

The setup panel has two modes. In Gallery and List (the liveries are in the gallery) its variants are such a list, `setup-layout.ts` (tested): they take what they need, past three rows they scroll. Whether a list scrolls is decided on the full width, then the list lays its tiles out in the width its bar leaves, so the layout cannot swing. Rebuilt for another aircraft, the variants list opens on the selected variant. Reported on 2026-10-27: the iFly 737 MAX (one variant per livery) and the FS Reborn Phenom 300E (eight variants with long names) pushed the liveries, tail number and buttons out of the panel.

The Showcase view (`default-grid.ts`, tested; named Default before) is drawn by the mod: two rows of the sim's large aircraft tiles in column hosts of a `<real-scroll direction="x">`, sized from the block's height and width as the sim's own grid is (the list ends 24 units above the block's bottom). The list rests on whole columns: the mod stops the sim's own wheel step (a third of a column) and moves one column per notch of a mouse wheel, 100 of delta (`WheelSteps`, `core/wheel-steps.ts`: a touchpad's small deltas add up; fast notches go on from the column the previous ones aimed at); 150 ms after the last `ui-scroll` or wheel event it settles on the nearest column or on its end (`settleOnStep`), except while a mouse button pressed in the gallery is held (the bar dragged and paused): then it settles at the release, a capture `mouseup` on the window or the first `mousemove` that reports no button held. The same code (`keepOnSteps`, `sim/step-scroll.ts`) keeps the Showcase panel's grid of small liveries on whole rows.

The Showcase panel (`showcase-mode.ts`, `showcase-layout.ts`; the panel in Gallery and List is the one above): every part at a fixed place, whatever the aircraft. `showcasePlaces(width, height, headerHeight, unit, count)` (pure, tested) gives the places, from the title block's bottom (the statistics' top) to the bottom of `Fleet_Details`: the variant row (as high as the livery header), the livery header, the large livery (as wide as the panel, in the sim's livery ratio, `LIVERY_RATIO`), the grid of small liveries (two rows of three) and the bottom block (two rows and their gap, on the panel's bottom). The five gaps between the title block and the bottom block are equal, in whole pixels: what the parts leave, divided by five and rounded down, the 0 to 4 pixels left going to the large livery's height (10 pixels at 1164 lines, 8 at 1080, 11 at 1440, 16 at 2160 with the option at 50). Only the grid's columns depend on `count`; nothing else depends on the aircraft. At the gaps' minimum (`GAP`, 6 units: a column too wide, see below) the large livery gives up height instead (`cropped`, its image cropped toward the top: 12 % of the cut above it, so that the fin stays whole). The parts are placed by top and height in the 250 ms pass, written only on change (`setStyle`), and nothing is written while the large livery is lower than a thumbnail (`panelHasRoom`: the screen animates; the panel keeps its Showcase places then, or stays hidden when it has none yet). The statistics are hidden (restored on leaving). The mode follows the gallery's flag (`liveriesInGallery`): the gallery mounts right after the setup feature, so the panel's first pass and the column's first width wait for a timeout of 0 (no Showcase form for one pass on entering Gallery or List), and the panel is hidden until then. Without the gallery feature the flag is never set: the panel always takes its Showcase form, over the sim's own grid. The variants list is hidden in Showcase and measures nothing then (`VariantsList.measure` needs a width); it is measured again at the next Gallery or List pass.

- Variants: a header row (`variant-dropdown.ts`) with the sim's word, `TT:MANUFACTURE.BREADCRUMB.VARIATION` ("Variant"), on the left, and over its whole box the sim's `Dropdown`, redrawn only when the variants or the selection change, `Disabled` with one variant (it does not open). The dropdown's own `Background` is hidden unless it is hovered (`opacity`, only when the row is not `:hover`), so that the header's background shows at rest and the sim's white Hover state fills the row, the title then in the dropdown's dark text colour; its text is on the right, always 12 units after the title (`--msfs-ui-variants-left`, measured) and before its arrow; a label too long for that place has its text reduced to fit (`TextFitter`, as the title block's lines: never cut, never scrolled), and so has each item of the open list, at each layout pass and after each scroll of the list (its items are recycled). When the variants' models differ, each variant whose model no other variant shares reads its model, the others their sim's title (`variantLabels`, `sim/aircraft-names.ts`, tested: A320, A320, A321 keep two titles): some add-ons name a variant after a livery (the Just Flight 146-200QC's read "146-200 QC Royal Air Force, 32 Squadron, ZE708 CMk3", their models 146-200, 146-200QC and 146-200QT). The models come from `GetAircraftFromVariationId` (`readVariantModels`: kept while the sim runs; one read at a time per variant; a variant the sim does not answer for is not asked again while the aircraft stays): the dropdown shows the titles (or the models already known) at once and is relabelled when the models arrive, the rest of the panel never waiting for them (0.6 s for the 146-200QC). Its open list ends on the large livery's bottom whatever the count: `List_Size` is the room below the row (`layout` with `dropdownListWithin`, `sim/dropdown-list.ts`), the items at the top, the rest an empty band; it is scrolled to the selected item on opening (the Dropdown keeps its scroll position between openings).
- Current livery (`large-livery.ts`): the sim's `ImageButton_Livery` at the large size, and inside its element (so that it keeps its Hover state) the two arrows (`IconButton_Squared` with `Icons/General/ArrowFull.svg`; the sim has no left arrow file: its own carousel, `Reno_SetupLiveryBlock`, turns the right one with `--rotation: 180deg` on the component), the position text and the heart. The wheel (capture phase) steps through `WheelSteps`. The order is `orderLiveries` (favourites first, kept while the variant stays); the grid shows the same list.
- Steps (`livery-stepper.ts`, pure, tested): a step shows the livery at once and is sent after 300 ms of quiet (`LIVERY_SETTLE_MS`, debounced); sends are numbered (`LiverySends`) so that only the last one's refusal gives the livery back; a livery sent and not yet reported by the sim stays shown (`sentId`), until a reload reports it or for 10 s (`2 * ANSWER_TIMEOUT_MS`, `expired`) after the configurator took it: then the large livery, the grid's outline and the header follow the configurator again; a send that follows one not reported yet (`overSent`) goes through `chooseLiveryWhileSending`, which does not skip the livery the configurator's last state still lists as selected (a return to the livery the sim is leaving would be lost); unavailable liveries are skipped (the stepper only holds the available ones and the selected); a step waiting is dropped when the variant or the aircraft changes (`dropStep`, `drop`). A click in the grid is sent at once through the same path.
- Grid (`livery-grid.ts`): a `<real-scroll direction="y">` of row hosts of three cells (row-major, `gridCell`), the cells recycled by a `PooledCells` pool along y with margins of 150 / 250 units (the gallery's are 300 / 600); each cell is an `ImageButton_Livery` with the mod's heart inside it; the shown livery has the component's `Selected` state. Two whole rows are in view, never a cut thumbnail at rest: one thumbnail size for every aircraft (the room of the sim's scroll bar, 20 units, always kept out of the width), in the sim's proportions; six liveries or fewer, no bar and the columns spread so that the outer ones reach both edges of the panel (`columnGap`, `lastGap`: the second gap takes the pixel the first leaves); more, the sim's bar on the right and the columns 6 units apart. The list rests on whole rows (`keepOnSteps`): one row per notch of the wheel, the bar's drag settling on the nearest row 150 ms after it stops or at the release; the shown livery's row is brought into view by whole rows when it changes (`gridReveal`, tested: nothing moves if it is in view, else the grid moves as little as it can; the thumbnails coming into view get their components at once). Hovering a thumbnail shows its name in the livery header.
- Bottom block, two rows high, in two columns (`bottomColumns`, tested): on the left the sim's Configure tile (`TileButton_Watermark_Small`, `name="TileButton_Watermark_Small_Cockpit"`), as the sim draws it, as high as the two rows and their gap: its text size, gradient and key, its cockpit drawing (`Watermark`, 180 units square) cut by the tile's height; on the right the tail number's title and field, then Fuel and Payload and Identification. `ConfigureTile.place` moves the tile (absolute in `ButtonBlock`) in whole pixels; `restore()` puts the six original inline values back (scope, mode change, screen hidden). The right column is as wide as the wider of its rows (the needs measured once per unit and per label, ceiled; the tail field's need is a constant, `TAIL_FIELD_UNITS`), its title and Fuel keeping their need, the field and Identification taking the rest; the tile takes what is left, its need being its text whole, its key and paddings. Until the needs are measured (the sim gives the tile a size after the rest of the screen: 1.2 s after the panel showed, 2.9 to 3.9 s after the screen on a slow entry; the right column's needs are known at once), or while the column widens to them, the block is shared in halves (`sharedColumns`). ## Data stored in the sim

Since 2.0 the mod keeps its data in the **vault**: the `msfs-ui.wasm` module of the package writes it to files of its own `work` folder (`%APPDATA%\Microsoft Flight Simulator 2024\WASM\MSFS2024\msfs-ui\work\vault-a|b.head|data` on Steam), 300 ms after the last write of a burst, confirmed by the module once it is on the disk: it survives a restart, a Quit and a force-stop of the sim, with no profile save. `core/storage.ts` keeps its API (`loadData`, `saveData`, `deleteData`) over an in-memory copy loaded from the module at start-up; `sim/vault.ts` talks to the module over the CommBus (messages in `core/vault-protocol.ts`, format in [wasm/README.md](../wasm/README.md)). The snapshot is limited to 524,288 bytes; a value that exceeds it blocks the saves of the session (logged). If the module does not answer within 3000 ms (a package installed without it, or installed since the sim started: the sim reads a module only at its start), the mod keeps the sim's `datastorage` as described below, and says why (`window.__msfsUiRuntime.storage`: `kind` is `vault` or `datastorage`, `detail` says why; Compatibility page, Storage group). The data of 1.x comes over: when the vault has never saved anything (the first start of 2.0), the mod copies its keys found in `datastorage` into it once (favourites, tail numbers, last uses and choices, and since 2.0.4 the hidden aircraft, kept there while the module of 2.0.1 to 2.0.3 failed; `copyFromDatastorage`, `core/storage.ts`), and logs which. Since 2.0.7, once the module confirms that the vault holds the data on the disk (`Vault.whenSaved`), the mod removes its keys from `datastorage` (those it copies, and `FAVORITE_AIRCRAFT` and `AIRCRAFT_USES` of earlier versions; `clearDatastorage`) and asks for one profile save, at every start that finds some there: before, a new vault (after *Uninstall everything*, or its files deleted) took them back (the owner, 2026-10-31: 50 hidden aircraft came back). Not confirmed, they stay (logged). A session that falls back then starts from an empty `datastorage`, and its changes give way to the vault's values when it answers late (`moveSessionWrites`).

**The fallback, `datastorage`** (the sim's persistent storage, where the menu keeps its own layout): it survives restarts, provided the sim saves its profile. The sim keeps it in memory and writes it to the disk only when it saves its profile (when one of its options is validated), not after a write nor when it quits: every write of the mod (`saveData`, `deleteData`) asks for a profile save, 2 s after the last of a burst (`sim/profile-save.ts`: the flow event `VALIDATE` for *Show the white dot cursor in freelook*, with its current value, so nothing changes; the option is declared in `compat.json` "options"). The browser's `localStorage` is emptied at every start: the mod never uses it. Every key starts with `MSFS_UI_` and holds JSON. In this fallback the keys are the same as in 0.3.0, so earlier data carries over (not into the vault). On one user's sim (a Microsoft Store install; other Store users have no such problem), `datastorage` is missing from the menu: nothing is kept there in the fallback (see [docs/next-steps.md](../docs/next-steps.md), 1.5, and the storage section of [docs/sim-reference.md](../docs/sim-reference.md#storage-and-translation)).

A stored value is not trusted: each reader keeps only what has its type (`storedObject`, `core/storage.ts`; the favourite liveries and the uses in `sim/favorites.ts`, the tail numbers in `sim/liveries.ts`, the hidden aircraft in `sim/hidden.ts`, the memories in `weather-bar/memory.ts` and `aircraft-gallery/memory.ts`), so that a damaged value (another version, a write cut short) gives defaults instead of a wrong value sent to the sim.

Aircraft are identified by `variationId` (stable); `aircraftId` may change when an aircraft is installed, so the mod looks it up when loading.

- **With the vault**, the keys are in the module's files, not in `datastorage`: read the mod's copy with `msfs-ui-dev eval "window.__msfsUiRuntime.storage"` (`kind`, `detail`); the commands below concern the fallback.
- **Reading or deleting a key** by hand (sim running, fallback): `msfs-ui-dev eval "datastorage.getData('MSFS_UI_FAVORITE_LIVERIES')"`. Unload the mod first (`window.__msfsUiRuntime.unload()`) before deleting a key: while it runs, it may write the key again at once. A deletion alone may not be saved (seen on 2026-10-16: a deleted key came back after a restart; the sim may write its storage only on a `setData`): after a deletion, any write of another key saves it.
- **Default tail number**: if `MSFS_UI_BASE_TAIL` is deleted, the mod records it again from the sim's field, often the last number applied; set it with `datastorage.setData('MSFS_UI_BASE_TAIL', JSON.stringify('ASXGS'))` to keep a precise default.

## Start-up and hot reload

1. The first log line is `[msfs-ui] module loaded (version …, build …)`. The app's compatibility check counts console errors from the latest such line on; it comes before the unload of the previous version, so a failing cleanup still counts.
2. `startRuntime()` unloads the previous version (`window.__msfsUiRuntime.unload()`), then registers this one.
3. The settings are imported from `/msfs-ui/config.js?t=<now>`:
   - The query string bypasses the page's module cache, so after a change in the app a hot reload is enough. There is no need to restart the sim.
   - When the file is missing or invalid (load error, not an object, another `schemaVersion`), the mod logs an error and runs with the catalogue defaults.
   - When single values are wrong, each one takes its default or is brought into range, and each adjustment is logged.
4. The mod opens the vault (`sim/vault.ts`) before the features: it asks the vault module for its snapshot, repeating the request every 500 ms, and waits up to 3000 ms. If the module does not answer, the data stays in the sim's `datastorage` for the session (the reason is logged and shown on the Compatibility page). A listener stays until the mod is unloaded: a module that answers after the bound is logged (`the vault module answered after N ms`) and noted in the storage detail, but the session is not switched to it.
5. The theme stylesheet is injected. Then each enabled feature starts in its own child scope of the root. If the start throws or its promise rejects, that scope is disposed and the feature is listed in `failed`.
6. `window.__msfsUiRuntime` exposes `version`, `build`, `settingsSource`, `settings`, `storage` (`kind`: `vault` or `datastorage`, and a `detail` read live: sequence number, size and keys of the vault, or the reason for the fallback), `started` and `failed` to the app and to `msfs-ui-dev eval`.

Verified in the sim (1.9.18, `fs-base-ui` 0.1.10) on 2026-10-17:
- `config.js` is read by the real menu;
- a settings change applies after a hot reload;
- a syntax error, a wrong schema version and a missing file each fall back to the defaults, with an explicit error;
- `unload()` removes the handle and the stylesheet;
- a file **added** to the mounted package (not listed in the `layout.json` the sim read at start-up) is not served until a restart, while files listed then are re-read on the fly, even if deleted and written again. The app's installer therefore asks for a restart whenever the new package has a file that did not exist when the sim started.
