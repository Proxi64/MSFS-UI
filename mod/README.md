# msfs-ui, the menu mod (1.0)

The part of MSFS-UI that runs inside the MSFS 2024 main menu. It is one ES2017 module, `dist/main.js`, which MSFS-UI-GENERATOR embeds and copies into the Community package as `html_ui/msfs-ui/main.js`. The app also writes the user's settings next to it, as `html_ui/msfs-ui/config.js` (see [Contracts between the app and the mod](../docs/development.md#contracts-between-the-app-and-the-mod)).

Node is needed only to build the mod, never on the user's machine.

## Commands

Run them from `mod/`:

```powershell
npm install          # once: esbuild, TypeScript, Ajv, Node types (exact versions)
npm run build        # dist/main.js, after every check below (with an inline source map)
node build/build.ts --release   # the same without the source map: the module shipped in the app
npm test             # unit tests (node:test); needs a build first (src/generated/)
npm run check        # build, then tests
```

To try the mod in the sim, use the developer tool of the app:

```powershell
generator\MsfsUi.DevTool\bin\Debug\net10.0-windows\msfs-ui-dev.exe install [--settings file]
msfs-ui-dev reload                       # hot reload while the sim runs
msfs-ui-dev console "[msfs-ui]"          # the mod's log
msfs-ui-dev eval "window.__msfsUiRuntime.settings"
msfs-ui-dev check                        # compatibility, offline and live
```

`--settings` takes a file in the app's settings format:
- `{ "schemaVersion": 1, "features": { "<id>": { "enabled": …, "options": { … } } } }`;
- without it, `%LOCALAPPDATA%\MSFS-UI-GENERATOR\settings.json` is used if it exists, otherwise the defaults of `features.json`.

## Contracts with the app

| File | Content | Read by |
|---|---|---|
| `features.json` | Every feature: id, title, description, screen, `enabledByDefault`, typed options (`boolean`, or `number` with `min` / `max` / `step` / `unit`) and their defaults | The build (typed settings, consistency checks) and the app (Features page, settings validation) |
| `compat.json` | What the mod takes from the sim: readable exports, screens, the sim's components it creates (with the attributes, states, values and children it uses), anchors, data-model symbols, files, CSS variables, translation keys, live checks | The app's compatibility check |
| `schema/*.schema.json` | JSON schemas of both files | The build (Ajv) and editors (`$schema`) |
| `test/fixtures/config.*.js` | Settings modules generated by the app (`ConfigScript`) | `ModContractTests` (C#) writes and compares them; `config-contract.test.ts` reads them with the mod's code |

After a change of `features.json`:
1. Run `dotnet test generator/MsfsUi.slnx` with `MSFS_UI_UPDATE_FIXTURES=1` to rewrite the fixtures.
2. Run `npm run check` here.

The version in `package.json` and the `modVersion` of `features.json` must be equal.

## What the build checks

`build/build.ts` stops with exit code 1 on the first failing step:

1. `features.json` and `compat.json` match their schemas. The catalogue also passes the rules a schema cannot express: unique ids, `min ≤ max`, and defaults within range and on the step grid.
2. `src/generated/catalog.ts` is generated from `features.json`: the `Settings` type, `FEATURE_IDS` and the specs used to validate `config.js`. It is not committed.
3. Feature modules match the catalogue:
   - each feature lives in `src/features/<id-in-kebab-case>.ts` or in a folder of that name;
   - it reads every one of its options as `settings.<option>`;
   - it is registered in `src/features.ts`, and a feature without a module has a `null` entry.

   The registry's type also refuses a missing or unknown feature id.
4. Everything the sources take from the sim is listed in `compat.json`:
   - screen and component GUIDs;
   - `name="…"` anchors, or children declared by a component;
   - `TT:` translation keys;
   - named imports of `/Global/…` modules;
   - `coui://html_UI/VFS/…` files;
   - the sim's CSS variables (`--color…`, `--fontSize…`, `--unscaledScreenHeight`, `--backgroundOpacity`).
5. No raw U+2028 / U+2029 in the sources: build them with `String.fromCharCode`.
6. `tsc` on the mod (`tsconfig.json`) and on the Node code (`tsconfig.node.json`, build and tests), both strict.
7. esbuild bundles `src/main.ts` into `dist/main.js`:
   - target ES2017, ASCII output, inline source map (none with `--release`);
   - the sim's `/Global/*` modules stay external, `.css` files are imported as text;
   - the module is then refused if it has an operator before `await` (`!await x`), which Coherent GT does not load.

## The sim's own components

What the mod shows is made of the sim's components wherever one exists, so that it looks and behaves exactly like the sim: markup, visual states (hover, selected, disabled), sounds and accessibility. `src/sim/components.ts` creates them; verified on sim 1.9.18 (`fs-base-ui` 0.1.10):

- `window.ResourcesManager.createElementFromGuid(guid, factory)` builds a component from its cooked template (`cookedcomps/{GUID}.html` and `.json`). `factory` only needs `createElementFromName(tag)`, which creates the bare `ui-resource-element`.
- Once `loadingList.whenAllLoaded` (and the manipulator's `refLoadingPromise`) resolve, `manipulator.activate()` is called, as the sim does for the components it creates on the fly. On dispose: `manipulator.deactivate()`, then removal.
- Exposed attributes (`Title`, `Text`, `Icon`, `Status`…) are set with `setExposedAttribute`; selection and disabling go through the component's traits: `traits.selectable.Set(true)` selects it, `traits.deactivable.Set(true)` disables it.
- A component whose template has no `selectable` trait (`TextTab`) gets one with `AttachTrait(element, 'selectable', trait)`, the trait being found by its `traitName` in `GuidToTrait`; it is detached with the component.
- Clicks reach the component as ordinary `click` events (its template sets `data-input-group`).
- The template positions the component in the sim's own layout: here it fills a host element that the feature's CSS sizes. A component made for larger sizes may need a layout rule on one of its children (the weather bar resizes `TileButton`'s `CornerWhite`, centres its `Content` and gives its `Background` the icon buttons' gradient; the favourites set `Marketplace_Tile_Horizontal`'s `Title` and `Creator` sizes; the presets dropdown moves its `Content` 12 units in and its `List`); such children are declared in `compat.json`.

Components used:
- `TileButton` (choice tiles; in compact hosts, `msfs-ui-compact-tile` in theme.css centres the title on one line and reduces the selection corner);
- `IconButton_Squared` (icons), `TextTab` (tabs), `TextButton_Small` (buttons; the gallery's Hidden and Favorites get the mod's icon before their `Text`, in the button's content row);
- `FreeFlight_IFR` (flight category, whose colours are the component's own exposed values);
- `ImageButton_Livery` (livery thumbnails: `manipulator.setData(image, onClick)`; it has no Disabled state, its host is dimmed);
- the mod's own icons (`core/icon-toggle.ts`, SVG in `currentColor`, not the sim's components: the owner's choice): a heart for the favourite liveries (empty; full for a favourite; white) and a slashed eye for the hidden aircraft; a click does not reach the tile under it;
- `Search_Input` (text fields, see below);
- `TileButton_Fleet` (gallery tiles: the mod writes AircraftImage and three lines of text, as the sim's `SetData` would: the name in AircraftName, the variant in Subtitle, the studio in Distance, which moves up to Subtitle when there is no variant. The tile's own `State_Distance` shows that third line, but its Disabled state hides it again for good, so the CSS shows it (`has-third-line`). Its template splits its height 1.4 (image) to 1.2 (text banner): the image area keeps that height (`--tile-image-h`) and the banner only takes its three lines, 75 units. The tile's own `tileClick` / `tileHover` events, which carry no data then, are stopped at its host, and the mod sends its own with the aircraft);
- `Marketplace_Tile_Horizontal` (the gallery's list rows and the Free Flight favourites: Image, Title, Creator; in the gallery on one line centred in the row, the name in the bold Title, "- studio - variant" in the light Creator; its rating, separator, price banner and own heart are hidden, the mod's icon (the eye of an aircraft, the heart of a livery) is in the row's top right corner; its `ImageBlock` takes the thumbnails' ratio, 720 × 344, since its own wider box with `object-fit: cover` cut a quarter of each thumbnail; its manipulator gets an owned `item`, which its hover handler reads. On Free Flight it keeps its own two lines: the name, then "variant · livery · tail number", the text stopping before the row's corner icon, the heart);
- `Dropdown` (the gallery's sort and the weather bar's added presets: `setData(items, current)` with `{ title, selectedCallback }` items, `setEmptyTitle`, `List_Size` = 33 units per item + 9: items of 30, 3 apart, 6 of padding above and below, in its `List` › `real-scroll`, a virtual list of the sim that recycles about 15 items whatever their number). Its template places the list 30 units under its top; the weather bar puts it right under the dropdown (`top: 100%`), sizes it to the bottom of the panel's last buttons and puts the room its whole items leave into the content's top padding. The list keeps its scroll position from one opening to the next (in the middle of an item after a change of resolution): the bar scrolls it on opening, by the items' spacing on the screen.

Lists that scroll use the sim's own scrolling element, `<real-scroll direction="y">` (created with `document.createElement`, as in the sim's cards): it scrolls on the wheel and draws the sim's scroll bar (`ui-scroll-bar`, disabled while the content fits). Children appended to it go into its content (`.scroll__content`, a plain block that the feature's CSS may turn into a flex container of wrapped rows, with room on the right for the bar; the gallery computes its columns on the content's `clientWidth`, which the bar already narrows); it is emptied child by child, never with `innerHTML`, which would remove its own structure. Its API: `currentScroll`, `maxScroll`, `scrollToPosition(px)`, `updateSizes()`, and a `ui-scroll` event on every move. The bar sits beside the content in `.scroll__bar-container`, 0 wide while the content fits and 10 pixels at 1440 lines once it scrolls (from the next frame).

The setup panel puts its variants and its livery thumbnails in two such lists sharing the room left by its headers, tail number and buttons (`setup-layout.ts`, tested): the variants take what they need while the liveries keep two rows; past that the variants keep three rows and both scroll. Whether a list scrolls is decided on the full width, then the list lays its tiles out in the width its bar leaves, so the layout cannot swing between the two. Rebuilt for another aircraft, the variants list opens on the selected variant. Reported on 2026-10-27: the iFly 737 MAX (one variant per livery) and the FS Reborn Phenom 300E (eight variants with long names) pushed the liveries, tail number and buttons out of the panel.

The Default view (`default-grid.ts`, tested) is drawn by the mod: two rows of the sim's large aircraft tiles in column hosts of a `<real-scroll direction="x">`, sized from the block's height and width as the sim's own grid is (the list ends 24 units above the block's bottom). The list rests on whole columns: the mod stops the sim's own wheel step (a third of a column) and moves one column per notch of a mouse wheel, 100 of delta (`WheelColumns`: a touchpad's small deltas add up; fast notches go on from the column the previous ones aimed at); 150 ms after the last `ui-scroll` or wheel event it settles on the nearest column or on its end (`settleColumn`), except while a mouse button pressed in the gallery is held (the bar dragged and paused): then it settles at the release, a capture `mouseup` on the window or the first `mousemove` that reports no button held.

The side by side layout (option `layout` of the gallery, `sideBySide`): the gallery cuts its right block in two (`splitColumns`, tested) so that three aircraft tiles and two livery tiles per row get the same width while the liveries scroll (when they do not, their tiles fill the column and are a little wider: 342 px against 322 px for the aircraft tiles, measured at 3440 × 1440), 12 units apart, each column keeping room for its scroll bar. The livery column (`liveries.ts`) has a header as the setup panel's, then the sim's `real-scroll`: in Gallery, the sim's `TileButton_Fleet` with the column's own `--tile-w` / `--tile-h` / `--tile-image-h` (image in the thumbnails' ratio, 720 × 344, two lines of text: the livery's name in `AircraftName`, its tail number in `Subtitle`); in List, `Marketplace_Tile_Horizontal` rows (name in `Title`, tail number in `Creator`). The tail number is the one the mod would apply: chosen for the livery, then the `atc_id` of its `livery.cfg` (read once, for the tiles near the view), then a registration in its name. The column reads and acts through `sim/configurator.ts`, as the setup panel. The setup panel sets the other flag of `sim/selection-layout.ts` while it covers the left column: the gallery then sends no `tileHover` to the page, so the column's header stays on the selected aircraft (the panel shows the configurator's) and the sim does not load, for every tile passing under the mouse while scrolling, statistics the panel hides (`GetAircraftWithCompareVariation`, after 100 ms). While it shows, the gallery sets the flag of `sim/selection-layout.ts`: the setup panel hides its livery header and list (`display: none !important`: the sim's list has a display of its own) and gives the variants the room, and the setup feature narrows the left column to 400 units (it checks the flag every 250 ms; the `widenColumn` option applies again when the column goes). The sim's `real-scroll` also has `flex-grow: 1` of its own: the variants list is fixed to the height `panel.ts` gives (`flex: 0 0 auto !important`). In List, the rows' `TitleBlock` stops 40 units from the right (before the corner icon) and is cut there, in both layouts; side by side, it shows the tile's own two lines (name, then "studio · variant"), each as wide as the block, so that every text is cut by its own box before the icon (a name is never wider than the block in the one-line rows either). The aircraft rows keep one width, in whole pixels, whether their list scrolls or not (`aircraftRowWidth`, tested: the bar's room and its 10 pixels at 1440 lines kept; the Hidden view's short list made them 10 pixels wider), and stand on the gallery tiles' edges, 6 units in from the list's, never over the scroll bar's room (`aircraftEdges`, tested): the bar above them does not move between Gallery and List (measured at 1440 lines: 1120 to 2118 in both; 8 pixels to the left in List before 2.0.1); the livery tiles and rows go to the header's right edge while they fit, the two tiles of a row a whole number of pixels apart so that the second ends on the edge (`liveryFit`, tested, `is-full-rows`; decided on the full width); when the list scrolls, the bar and its room are kept. Side by side, the bar is cut the same way (`is-split`, two parts in one bar, their widths written by the layout pass): search, count, Hidden and Favorites above the aircraft tiles, from the first tile's left edge to the last one's right edge (the rows' edges in List), not over the scroll bar (`aircraftBarEdges`, tested); the sort dropdown, its direction and Gallery, List, Default above the livery column, from its left edge to its right one, the dropdown taking what the others leave (172 units at 16:9 and wider: the selection's content is 1920 units wide). In the Classic layout the bar stays one line. When the search would be narrower than 240 units, the count drops its total (`shortCount`, tested; side by side the search spans only the first part of the bar, so it is narrower than in the Classic layout; whether the count shortens at 16:9 has not been measured, only at 3440 × 1440).

The gallery and the livery column keep components only for the tiles near the visible part of the list, recycled as the sim's own grid does (`core/virtual-list.ts`, `sim/component-pool.ts`): one of the sim's aircraft tiles is about 110 elements and every change of layout lays them all out again (149 tiles alive: 156 ms per change at 3440 × 1440, against 4.8 ms without them); creating tiles while scrolling stutters as if loading all the time. A pool of slots (a card and its icon) moves them between the cells within 300 units of the view; a slot farther than 600 units waits in a hidden parking (out of the layout) and is given to the next cell with its new data. A new slot makes its components in a hidden staging area and joins its cell once ready: the sim refuses a component moved or removed while it sets up (one exception left: switching between Gallery and List disposes the old pool, slots still loading included; see next-steps). Positions are all read before any change, so the engine lays the page out once per pass. The tiles are updated in place when the set of tiles is unchanged. Favourites always come first, whatever the sort; Name (the displayed name, in natural order: ATR 42, ATR 72, Cessna 172) and Studio (then name) are sorted by the mod, Max Range by the sim; a sort change starts from the first aircraft. The sim's list keeps the order sent to it: the gallery sends its own order back (the first of the sim's sort options, Max Range on 1.9.18, not reversed) for the mod's sorts and when it closes. Names and studios are trimmed (some publishers end them with a space). Behind every thumbnail, a gradient measured on the sim's studio backdrop shows through the few transparent ones (Nemeth Designs' EC-135), which would otherwise show the tile's dark colour.

Hidden aircraft (`sim/hidden.ts`; the rules are in `tiles.ts` and `sim/hidden.ts`, tested in `test/hidden.test.ts` and `test/aircraft-gallery.test.ts`): every aircraft tile and row has a slashed eye in its top right corner, in the same icon host as the Favorites tiles' heart (each slot of the pool has both, one shown), inside the card so that the pointer on it keeps the card hovered. A click hides the aircraft (all its variants: name and publisher), or brings it back when it is hidden; nothing goes to the sim or the configurator, so the selected aircraft can be hidden and stays selected. The gallery redraws on the change and keeps its scroll: the next tiles close the gap. The Hidden button (left of Favorites, never on together: turning one on turns the other off) shows only the hidden aircraft, their eye on. A hidden aircraft among the favourites put first (the frozen ids of the order) stays, veiled: a 35 % black layer over the card, under its icon, with a large slashed eye centred on the thumbnail (a marker: clicks go through to the tile), its eye on; the Favorites tiles of its liveries are veiled too, with the heart only. A hidden aircraft whose livery gets a heart while the screen stays shows at once, veiled, in its place (`keptAircraftIds`: the frozen ids and the favourites of now; favourites come first, without exception). One whose last favourite goes leaves when the order is set again. When the aircraft under the mouse leaves the list (hidden, filtered out), the left column's header goes back to the selected aircraft (the gallery sends `tileHover` without an aircraft, as on leaving a tile). The count is the tiles shown (veiled ones included) out of the category tab's aircraft. The Default view is filtered like the other two.

Texts too long for their place: the engine shows no ellipsis, and the sim's own tiles scroll such texts on hover (their `text-marquee` / `block-marquee`). The mod puts the sim's `marquee__trigger` class on each tile's host, so that hovering anywhere on the tile scrolls them.

Free Flight is laid out as one page (the owner's choices, 2.0.2). The gap between the groups of blocks is the same in both columns: the weather bar shares its column's free room, from the *Flight Conditions* widget down to the map buttons (`Worldmap_Filters`), evenly between the widget, its sections, the search field and the buttons, in whole pixels rounded to the nearest (`groupGap`: the METAR, shown at times, is not counted and takes from the room under the search field), never under `GROUP_GAP` (24 units, the sim's own gap under its aircraft button, measured at 1080, 1440 and 2160 lines), and writes it on the page element (`data-msfs-ui-group-gap`) for the favourites. Every block is as wide as its column, every text 12 units in, 6 units between a header and its content.

The weather bar (`weather-bar/`): *Today* (the times of day), *Weather* (the sim's presets, titled by a `TT:` key: Live on two cells, in the traffic tiles' `TileButton` with its name, the others as `IconButton_Squared`, six cells per row in whole pixels, the pixels left over given to the first cells of the rows, `layoutPresets`; the presets added by other packages, titled by their name and often without an icon the sim has, in a `Dropdown` under them, `presets.ts`), the METAR, *Air traffic* and *Multiplayer*. Its tiles take the icon buttons' gradient (`--colorPrimary` to `--colorGradient`) instead of their dark glass. It moves the sim's search field (`Searchblock`, an absolute child of the page) under its last block (the bar, or the sim's card on the Airport tab) by a class and CSS variables on that block, removed with the scope: as high as the time tiles (36 units, in the sim's unit: `--u` is not defined on the sim's elements), its 400-unit results list opening upwards, the block above the mod's panels (z-index 51; theirs is 50), hidden while a map panel fills the column or when it does not fit above the map buttons with `GROUP_GAP` under it. The last weather remembered keeps the preset's title (`rememberedPreset`, tested): the indexes move when a pack of presets is added or removed.

The Free Flight favourites (`freeflight-favorites/`): a card like the sim's (background layers, no header) under the sim's aircraft button, or under its "Search location" field while that one is still there (the weather bar turned off; then hidden while the search shows its results), as wide as the button, hidden when there is no favourite (no empty block: the owner's choice, 2.0.1); its rows in the sim's `real-scroll`, as many whole rows as fit (in whole pixels, as the engine lays them out), the others scrolling, the bar's room on the right (6 units from the rows) only when the list scrolls. The row's title (the aircraft) is 16 units, its second line 12, 6 units apart. One row per favourite livery; from the most recently used, an order kept while the screen stays on display. A click loads the variant then the livery (`loadAircraft`; the list is dimmed meanwhile, the card keeps the mouse lock); the row of the current aircraft is selected; the heart removes the favourite livery. The use of each aircraft (`trackAircraftUse`: last livery per variant, date of use of each favourite livery) is recorded at every change of aircraft, whatever the screen.

Text fields use the sim's `Search_Input`: its manipulator handles the keyboard as in the sim's own search fields, so the sim's shortcuts stay off while typing. The mod receives the text with `addChangeCallback`, entering and leaving with `addEnterCallback` / `addExitCallback`, Enter with `addSubmitCallback`, and writes with `setSearchValue`. `updateVisual({ forceInput: true })` gives the plain variant without the magnifier; the element keeps the flag through the manipulator's later updates. The engine shows no ellipsis for cut text: lists of names fit their layout to the measured text (the setup panel's variants: 3, 2 or 1 per row). What the sim draws without a component (card backgrounds, section headers, text) reuses the sim's markup: `blurredBackground`, the accessibility layer (`--colorComplementary2` at `--backgroundOpacity`), a black veil at 20 %, headers at 30 %, text in `--fontSizeXS`.

## Data stored in the sim

Since 2.0 the mod keeps its data in the **vault**: the `msfs-ui.wasm` module of the package writes it to files of its own `work` folder (`%APPDATA%\Microsoft Flight Simulator 2024\WASM\MSFS2024\msfs-ui\work\vault-a|b.head|data` on Steam), 300 ms after the last write of a burst, confirmed by the module once it is on the disk: it survives a restart, a Quit and a force-stop of the sim, with no profile save. `core/storage.ts` keeps its API (`loadData`, `saveData`, `deleteData`) over an in-memory copy loaded from the module at start-up; `sim/vault.ts` talks to the module over the CommBus (messages in `core/vault-protocol.ts`, format in [wasm/README.md](../wasm/README.md)). The snapshot is limited to 524,288 bytes; a value that exceeds it blocks the saves of the session (logged). If the module does not answer within 3000 ms (a package installed without it, or installed since the sim started: the sim reads a module only at its start), the mod keeps the sim's `datastorage` as described below, and says why (`window.__msfsUiRuntime.storage`: `kind` is `vault` or `datastorage`, `detail` says why; Compatibility page, Storage group). The data of 1.x comes over: when the vault has never saved anything (the first start of 2.0), the mod copies the keys of 1.x found in `datastorage` into it once (favourites, tail numbers, last uses and choices; `copyFromDatastorage`, `core/storage.ts`), and logs which; `datastorage` is left as it was.

**The fallback, `datastorage`** (the sim's persistent storage, where the menu keeps its own layout): it survives restarts, provided the sim saves its profile. The sim keeps it in memory and writes it to the disk only when it saves its profile (when one of its options is validated), not after a write nor when it quits: every write of the mod (`saveData`, `deleteData`) asks for a profile save, 2 s after the last of a burst (`sim/profile-save.ts`: the flow event `VALIDATE` for *Show the white dot cursor in freelook*, with its current value, so nothing changes; the option is declared in `compat.json` "options"). The browser's `localStorage` is emptied at every start: the mod never uses it. Every key starts with `MSFS_UI_` and holds JSON. In this fallback the keys are the same as in 0.3.0, so earlier data carries over (not into the vault). On one user's sim (a Microsoft Store install; other Store users have no such problem), `datastorage` is missing from the menu: nothing is kept there in the fallback (see [docs/next-steps.md](../docs/next-steps.md), 1.5, and the storage section of [docs/sim-reference.md](../docs/sim-reference.md#storage-and-translation)).

| Key | Content | Written by |
|---|---|---|
| `MSFS_UI_WEATHER_BAR` | `{ "weather": <preset index>, "weatherTitle": <the preset's title, a TT: key or an added preset's name; absent before 2.0.2>, "time": "now" \| "dawn" \| "day" \| "dusk" \| "night", "airtraffic": "AIRTRAFFICAI"…, "multiplayer": "MULTIPLAYEROFF"… }` (traffic keys absent until a click in those sections) | Clicks in the weather bar (option `remember`) |
| `MSFS_UI_WEATHER_BAR_TAB` | `"weather"` or `"airport"`: the last tab chosen when a card of the sim shares the column (`"airport"` also stands for the traffic card) | Clicks on the tabs |
| `MSFS_UI_FAVORITE_AIRCRAFT` | Favourite aircraft of the versions before 1.3.0 (a heart on the aircraft): **removed** at the first start of 1.3.0 (`dropFavoriteAircraft`, logged), the favourites being liveries since | None |
| `MSFS_UI_FAVORITE_LIVERIES` | Favourite liveries: `variationId`, livery folder (the form of `MSFS_UI_LIVERY_TAILS`; for a livery without one, the folder of its thumbnail), title, thumbnail, aircraft name, publisher, variant, date of last use | Hearts of the livery column, the setup panel and Free Flight; the date at each change of aircraft |
| `MSFS_UI_HIDDEN_AIRCRAFT` | Hidden aircraft: `[{ "displayName": …, "creator": … }]` (name and publisher, as the favourite liveries identify an aircraft) | The eye of the gallery's aircraft tiles and rows |
| `MSFS_UI_AIRCRAFT_GALLERY` | `{ "view": "gallery" \| "list" \| "stock", "favoritesOnly": …, "hiddenOnly": …, "sort": { "option": "name" \| "studio" \| <the sim's option key>, "reversed": … } \| null }` (`stock` is the Default view; the 0.3.0 key `TT:MENU.NAME` reads as `name`; `hiddenOnly`, the Hidden filter, absent before 2.0.0; both filters true, never written, reads as Favorites; a `lastView` stored by 2.0.1 is dropped) | The gallery's controls |
| `MSFS_UI_AIRCRAFT_USES` | Per `variationId`: last livery (folder, title, thumbnail) and date of use; 60 variants at most | Recorded at each change of aircraft |
| `MSFS_UI_LIVERY_TAILS` | Per livery folder (lower case, for example `simobjects/airplanes/microsoft_sf50/liveries/microsoft/apex_corso_red`): the tail number chosen | Changes of the tail number field |
| `MSFS_UI_BASE_TAIL` | Default tail number: the sim's field the first time the mod reads it while the key is empty | Recorded once, or set by hand |

Aircraft are identified by `variationId` (stable); `aircraftId` may change when an aircraft is installed, so the mod looks it up when loading.

- **With the vault**, the keys are in the module's files, not in `datastorage`: read the mod's copy with `msfs-ui-dev eval "window.__msfsUiRuntime.storage"` (`kind`, `detail`); the commands below concern the fallback.
- **Reading or deleting a key** by hand (sim running, fallback): `msfs-ui-dev eval "datastorage.getData('MSFS_UI_FAVORITE_LIVERIES')"`. Unload the mod first (`window.__msfsUiRuntime.unload()`) before deleting a key: while it runs, it may write the key again at once. A deletion alone may not be saved (seen on 2026-10-16: a deleted key came back after a restart; the sim may write its storage only on a `setData`): after a deletion, any write of another key saves it.
- **Default tail number**: if `MSFS_UI_BASE_TAIL` is deleted, the mod records it again from the sim's field, often the last number applied; set it with `datastorage.setData('MSFS_UI_BASE_TAIL', JSON.stringify('ASXGS'))` to keep a precise default.

## Start-up and hot reload

1. The first log line is `[msfs-ui] module loaded (version …, build …)`. The app's compatibility check counts console errors from the latest such line on; it comes before the unload of the previous version, so a failing cleanup still counts.
2. `startRuntime()` unloads the previous version (`window.__msfsUiRuntime.unload()`), then registers this one.
3. The settings are imported from `/msfs-ui/config.js?t=<now>`:
   - The query string bypasses the page's module cache, so after a change in the app a hot reload is enough. There is no need to restart the sim.
   - When the file is missing or invalid (load error, not an object, another `schemaVersion`), the mod logs an error and runs with the catalogue defaults.
   - When single values are wrong, each one takes its default or is brought into range, and each adjustment is logged.
4. The mod opens the vault (`sim/vault.ts`) before the features: it asks the vault module for its snapshot, repeating the request every 500 ms, and waits up to 3000 ms. If the module does not answer, the data stays in the sim's `datastorage` for the session (the reason is logged and shown on the Compatibility page). A listener stays until the mod is unloaded: a module that answers after the bound is logged (`the vault module answered after N ms`) and noted in the storage detail, but the session is not switched to it.
5. The theme stylesheet is injected. Then each enabled feature starts in its own child scope of the root. If the start throws or its promise rejects, that scope is disposed and the feature is listed in `failed`.
6. `window.__msfsUiRuntime` exposes `version`, `build`, `settingsSource`, `settings`, `storage` (`kind`: `vault` or `datastorage`, and a `detail` read live: sequence number, size and keys of the vault, or the reason for the fallback), `started` and `failed` to the app and to `msfs-ui-dev eval`.

Verified in the sim (1.9.18, `fs-base-ui` 0.1.10) on 2026-10-17:
- `config.js` is read by the real menu;
- a settings change applies after a hot reload;
- a syntax error, a wrong schema version and a missing file each fall back to the defaults, with an explicit error;
- `unload()` removes the handle and the stylesheet;
- a file **added** to the mounted package (not listed in the `layout.json` the sim read at start-up) is not served until a restart, while files listed then are re-read on the fly, even if deleted and written again. The app's installer therefore asks for a restart whenever the new package has a file that did not exist when the sim started.
